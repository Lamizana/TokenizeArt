A Comprendre avant de coder

Pas de panique si certains mots te semblent étranges. Voici l'essentiel en 5 minutes.

A.1 Qu'est-ce qu'un NFT ?

Un NFT (Non-Fungible Token) est un jeton numérique unique créé sur une blockchain. Contrairement à un token classique (où chaque unité est identique et échangeable), chaque NFT est non fongible : il ne peut pas être remplacé par un autre à l'identique. Dans notre projet, il suivra la norme BEP-721 (la norme des NFTs sur la BNB Chain), calquée sur l'ERC-721 d'Ethereum.

Chaque NFT dispose d'un owner (propriétaire) et d'une tokenURI qui pointe vers ses métadonnées (image, nom, description). Grâce au standard, tous les wallets et explorateurs comprennent et affichent ton NFT automatiquement.

Différence clé : un token fongible (BEP-20) est comme des pièces de monnaie ; un NFT (BEP-721) est comme une œuvre d'art signée, avec un numéro d'inventaire unique.

A.2 Blockchain, testnet et le réseau réel

La BNB Chain (réseau du partenaire du projet 42) existe en deux versions :

  • Réseau principal (Mainnet) : le vrai réseau, avec de l'argent réel. On n'y touche pas pour ce projet.
  • Réseau de test (Testnet) : une copie gratuite pour s'entraîner. Les tokens s'y appellent des tBNB et ne valent rien. C'est ici qu'on va travailler.
Rassure-toi : ce projet ne demande jamais d'argent réel. Tout se passe sur le testnet.

A.3 Le vocabulaire à connaître

  • Wallet (portefeuille) : applis comme MetaMask qui détiennent tes adresses et tes fonds.
  • Adresse : une longue chaîne (0x...) qui identifie un compte, un peu comme un numéro de compte bancaire.
  • Smart contract : un programme qui vit sur la blockchain (ici : la fabrique qui crée tes NFTs).
  • IPFS : un système de stockage distribué de fichiers, idéal pour héberger l'image et les métadonnées d'un NFT de façon permanente.
  • CID : l'empreinte unique d'un fichier sur IPFS (ipfs://Qm...). Il sert à retrouver l'image n'importe où.
  • Métadonnées : le "dossier" du NFT (image, nom, artiste, titre...) stocké en JSON, souvent sur IPFS.
  • Gas : la petite redevance en crypto payée pour exécuter une action sur la blockchain.
  • Faucet : un site qui distribue gratuitement des jetons de test.
  • Block explorer (BSCScan) : un moteur de recherche de la blockchain, où chaque transaction est visible.
  • ABI : la "notice d'utilisation" d'un smart contract, décrivant ses fonctions.
Notre objectif : créer un NFT nommé Token42, avec une image stockée sur IPFS (le chiffre 42 doit y être lisible), le déployer sur la BSC Testnet, le miner, puis le vérifier sur BSCScan.

Objectif : avoir quelques tBNB sur ton wallet testnet.

D Créer l'image et la stocker sur IPFS

Avant le code, on prépare le « visage » de notre NFT : son image. Le sujet impose qu'elle soit stockée via un registre distribué (IPFS par exemple) et que le chiffre 42 y soit lisible.

Objectif : une image originale contenant le 42, disponible sur IPFS (obtention d'un CID).

D.0 Comprendre IPFS et le rôle de Pinata

Avant de manipuler Pinata, il faut saisir pourquoi on ne met pas simplement l'image sur un site web classique. C'est une question que les évaluateurs adorent poser.

Le problème du stockage centralisé. Si ton image vit sur un seul serveur (celui de ton hébergeur, d'un site, d'un réseau social…), tout dépend de ce point unique. Ce serveur peut :

  • tomber en panne → l'image disparaît ;
  • fermer ou supprimer le contenu → les liens deviennent "morts" ;
  • être censuré ou modifié sans ton accord.

Un NFT est censé durer et prouver durablement une propriété. Le lier à un serveur central fragile est donc contre-productif.

Qu'est-ce qu'IPFS ? IPFS (InterPlanetary File System) est un système de fichiers distribué et pair-à-pair. Contre l'approche centralisée, il introduit deux idées majeures :

  • Adressage par contenu : un fichier n'est pas identifié par son emplacement (comme une URL /images/token.png) mais par son contenu, via un CID (Content Identifier). Un CID est une sorte d'empreinte cryptographique du fichier — le même contenu donne toujours le même CID, partout sur le réseau.
  • Déduplication et immutabilité : deux personnes ayant le même fichier partagent le même CID. Et si tu modifies ne fût-ce qu'un pixel, le CID change complètement : un CID pointe donc toujours vers un contenu exactement identique et inchangé.

Épinglage (pinning) : sur IPFS, un fichier n'est lisible que si au moins un nœud le maintient en ligne. « Épingler » un fichier, c'est s'engager à le garder disponible. Sans épinglage, un contenu peut disparaître si personne ne le conserve.

Passerelles (gateways) : les navigateurs ne parlent pas IPFS nativement. Les gateways sont des sites web qui traduisent une adresse IPFS en URL web classique, par exemple :

https://gateway.pinata.cloud/ipfs/QmXy1...VOTRE_CID...

Pourquoi Pinata ? Pinata est un service d'épinglage (pinning service). Plutôt que de monter et entretenir ton propre nœud IPFS (technique, coûteux, fragile), Pinata héberge et épinglise tes fichiers pour toi, tout en offrant une interface web, des statistiques et une API. C'est l'un des prestataires les plus utilisés dans l'écosystème NFT.

Lien avec le sujet : le sujet exige un stockage via « registre distribué (IPFS, par exemple) ». Choisir Pinata pour héberger et épingler nos fichiers sur IPFS est donc un choix justifiable, que tu pourras défendre à l'évaluation.

D.1 Concevoir l'image

  • Choisis la représentation de ton œuvre : dessin, photo, design, texte stylisé… la liberté est totale.
  • Fais en sorte que le chiffre 42 soit clairement lisible dans l'image (c'est une exigence du sujet et il sera vérifié).
  • Interdit : tout terme ou image insultant, sous peine de sanctions.
  • Exporte au format .png ou .jpg (format recommandé pour les NFTs).
Ne stocke pas l'image dans ton dépôt Git comme unique copie : le sujet exige une technologie de registre distribué (IPFS). On s'en occupe à l'étape suivante.

D.2 Utiliser Pinata : uploader l'image

Pinata est un service simple pour héberger et épingler des fichiers sur IPFS. L'offre gratuite suffit largement pour ce projet.

D.2.a — Créer un compte

  1. Va sur https://www.pinata.cloud et clique sur "Sign Up".
  2. Crée ton compte (e-mail + mot de passe) et confirme-le.
  3. Le plan gratuit (free) suffit : il offre un quota de stockage et d'épinglage très large pour quelques fichiers.
  4. Une fois connecté, tu arrives sur le tableau de bord. L'onglet "Files" liste tes fichiers épinglés.
Optionnel : la clé API. Dans "API Keys", tu peux créer une clé (API Key + Secret) pour gérer tes fichiers par programmation. Ce n'est pas nécessaire pour le projet, mais utile si tu automatises via le site de mint (bonus M.2). Garde le secret confidentiel.

D.2.b — Uploader l'image

  1. Dans l'onglet "Files", clique sur "Add Files" puis "File".
  2. Sélectionne ton image (.png ou .jpg) ou dépose-la par glisser-déposer.
  3. Clique sur "Upload".
  4. Après quelques secondes, le fichier apparaît dans la liste avec une colonne CID (ça ressemble à QmXy1...). Clique sur l'icône de copie pour le récupérer.

D.2.c — Vérifier et comprendre

  1. Teste ton image à l'adresse https://gateway.pinata.cloud/ipfs/<CID> : elle doit s'afficher dans le navigateur.
  2. Comprends que ce CID est unique et figé : il identifie exactement ce contenu. Si tu changes l'image, tu obtiendras un nouveau CID (l'ancien restera intact).
  3. Reste épinglé : tant que le fichier est dans ta liste Pinata (Pinned), il reste disponible sur IPFS. Ne le supprime pas du tableau de bord.
PATIENCE — la propagation IPFS : un fichier tout juste publié peut mettre quelques secondes ou minutes à être visible via toutes les passerelles. Si le lien est vide, attends puis recharge.
Vérif : ton image s'ouvre via le lien IPFS = étape réussie.

D.3 Les alternatives à Pinata

Pinata est un excellent choix, mais il n'est pas le seul. Si tu préfères, ou pour défendre ton choix à l'évaluation, voici les principales alternatives pour stocker l'image et les métadonnées d'un NFT :

Autres services d'épinglage : on trouve aussi Filebase, Infura IPFS, ou MagicEden/arweave... La plupart reposent sur le même principe : ils épinglent ton fichier sur IPFS (ou un registre distribué équivalent) et te donnent un CID / identifiant.
Fait ton choix : le sujet impose « un registre distribué (IPFS, par exemple) ». Peu importe le prestataire tant que l'image et les métadonnées sont accessibles de façon durable via un identifiant de contenu. Pinata est recommandé pour sa simplicité, mais tu es libre.

E Créer les métadonnées (JSON) du NFT

Le NFT doit pointer vers un fichier JSON qui décrit ses métadonnées. Le sujet exige : le nom de l'artiste (qui correspond à ton identifiant), le chiffre 42 et un titre.

Objectif : un fichier metadata.json stocké sur IPFS, avec nom + artiste + 42 + image.

E.1 Rédiger le fichier metadata.json

Crée un fichier metadata.json de ce type (adapte les valeurs) :

{
  "name": "Token42 — Méditation au 42e étage",
  "description": "Un NFT unique créé dans le cadre du projet TokenizeArt (42 x BNB Chain). L'œuvre représente la réponse... et bien sûr, le 42.",
  "image": "ipfs://QmXy1...VOTRE_CID_IMAGE...",
  "attributes": [
    { "trait_type": "Artiste", "value": "alamizan" },
    { "trait_type": "Projet", "value": "TokenizeArt" }
  ]
}
  • name : le titre du NFT, contenant le chiffre 42.
  • image : le CID IPFS de l'image obtenu en D.2 (préfixe ipfs://).
  • attributes / Artiste : ton identifiant (ex. ton login 42). Le sujet veut que le nom de l'artiste corresponde à ton identifiant.
Attention : chaque champ doit être écrit en bon JSON (virgules, guillemets). Une erreur de syntaxe et le NFT s'affichera vide.

E.2 Uploader le JSON sur IPFS (Pinata)

  1. Reviens dans Pinata, onglet "Files" → "Add Files".
  2. Sélectionne metadata.json et upload-le (même procédure qu'en D.2).
  3. Récupère son CID (ex. QmAbc...). Attention : il diffère du CID de l'image — c'est normal, ce sont deux contenus distincts.
  4. C'est ce CID-là (JSON) qu'on mettra dans le smart contract comme tokenURI de base.
Immutabilité du CID : une fois que le JSON est référencé dans le contrat, son CID est figé. Si tu modifies le fichier, tu obtiens un nouveau CID et l'ancien NFT continuera de pointer vers l'ancien contenu. Il faut donc valider soigneusement le JSON avant de l'épingler en référence définitive. Pour un changement, publie un nouveau fichier (nouveau CID) plutôt que de modifier l'ancien.
Vérif : le JSON s'ouvre dans le navigateur via https://gateway.pinata.cloud/ipfs/<CID_JSON> et affiche bien le champ image avec le CID de l'image.

F Écrire le smart contract du NFT

On écrit le programme de notre NFT en Solidity. On réutilise la bibliothèque OpenZeppelin qui fournit un ERC-721 éprouvé (pas besoin de tout réinventer, c'est plus sûr).

Objectif : un fichier Token42.sol correct, commenté, avec les fonctions mint, ownerOf et une gestion de propriété sécurisée.

F.1 Le code complet du contrat

Ce fichier doit aller dans le dossier code/ de ton dépôt sous le nom Token42.sol. Voici un exemple de base (à adapter et à commenter toi-même pour l'évaluation) :

// SPDX-License-Identifier: MIT
// Token42 — NFT non fongible (standard BEP-721 / ERC-721) sur la BNB Chain
pragma solidity ^0.8.0;

import "@openzeppelin/contracts/token/ERC721/ERC721.sol";
import "@openzeppelin/contracts/token/ERC721/extensions/ERC721URIStorage.sol";
import "@openzeppelin/contracts/utils/Counters.sol";

contract Token42 is ERC721URIStorage {
    using Counters for Counters.Counter;
    Counters.Counter private _tokenIds;

    address public owner;
    string public baseURI;

    // Chaque NFT possède un numéro unique (tokenId)
    // et une URI pointant vers ses métadonnées (IPFS)

    constructor(string memory _baseURI) ERC721("Token42", "T42") {
        owner = msg.sender;   // Le déployeur devient propriétaire de la collection
        baseURI = _baseURI;
    }

    // Créer (miner) un nouveau NFT pour `recipient`
    function mintNFT(address recipient) public returns (uint256) {
        require(msg.sender == owner, "Token42: only owner can mint");
        _tokenIds.increment();
        uint256 newTokenId = _tokenIds.current();
        _mint(recipient, newTokenId);
        _setTokenURI(newTokenId, baseURI);  // pointe vers metadata.json sur IPFS
        return newTokenId;
    }

    // Récupérer le propriétaire d'un NFT donné (exigé par le sujet)
    function ownerOf(uint256 tokenId) public view override returns (address) {
        return super.ownerOf(tokenId);
    }

    // Transférer la propriété de la collection
    function transferOwnership(address newOwner) public {
        require(msg.sender == owner, "Token42: only owner");
        owner = newOwner;
    }
}
À toi de jouer : ce code est une base. Commente chaque fonction avec tes propres mots — une revue de code aura lieu à l'évaluation. Vérifie notamment que ownerOf est bien présent (exigence du sujet).

F.2 Expliquer les mots du code

  • contract Token42 is ERC721URIStorage → on hérite du standard NFT d'OpenZeppelin + du support des URI stockées.
  • _tokenIds → un compteur qui attribue un numéro unique à chaque NFT (1, 2, 3…).
  • mintNFT → crée réellement le NFT et lui associe ses métadonnées (l'URI IPFS).
  • ownerOf → répond « qui possède ce NFT ? » (fonction exigée par le sujet).
  • require(...) → vérifie une condition, sinon annule la transaction. Ici : seul le propriétaire peut miner.
Pourquoi un seul owner ? Le sujet parle de sécurité (propriété / privilèges). On restreint le mint au propriétaire pour contrôler qui crée les NFTs. C'est un choix sûr et simple à défendre à l'oral.

G Compiler avec Remix

Remix IDE est l'outil recommandé par le sujet : un environnement gratuit dans le navigateur pour écrire, compiler et déployer des smart contracts.

Objectif : ton code compile sans erreur.

G.1 Ouvrir Remix et créer le fichier

  1. Va sur https://remix.ethereum.org.
  2. Dans le panneau de gauche (explorateur de fichiers), crée un dossier contracts s'il n'existe pas, puis un fichier Token42.sol (icône "nouveau fichier").
  3. Colle le code du contrat dedans et enregistre (Ctrl+S).

G.2 Installer OpenZeppelin (import)

Le code importe @openzeppelin/contracts/.... Remix doit le télécharger :

  1. Ouvre l'onglet "Solidity Compiler" (icône en forme de "S").
  2. Clique sur "Compile Token42.sol". Remix détectera l'import manquant et proposera de l'installer — accepte.
  3. Sinon, va dans l'onglet "File explorer" → clic droit sur le dossier racine → "Import from GitHub" et colle : OpenZeppelin/openzeppelin-contracts@master/contracts/token/ERC721/ERC721.sol. Remix récupérera toute la bibliothèque.

G.3 Choisir la version et compiler

  1. Dans "Solidity Compiler", choisis la version 0.8.x (ex. 0.8.26) — elle doit correspondre à pragma solidity ^0.8.0.
  2. Clique sur "Compile Token42.sol".
  3. La barre verte "Compilation successful" doit s'afficher.
Erreurs fréquentes :
  • Source file requires different compiler version → change la version sélectionnée en 0.8.x.
  • SPDX license identifier not provided → la ligne // SPDX-License-Identifier: MIT est absente, ajoute-la.
  • Different argument count / Unknown function → vérifie que tu es bien sur ERC-721 (pas ERC-20) et que _setTokenURI existe (via ERC721URIStorage).

I Miner (mint) ton NFT

Le contrat est déployé, mais aucun NFT n'existe encore : il faut le « miner », c'est-à-dire appeler la fonction mintNFT.

Objectif : au moins un NFT miné, avec son propriétaire identifiable via ownerOf.

I.1 Appeler mintNFT

  1. Toujours dans Remix, section "Deployed Contracts" → ton contrat Token42 déployé.
  2. Déplie la liste des fonctions et trouve mintNFT.
  3. Renseigne l'adresse du destinataire (choisis ton adresse MetaMask pour être le premier propriétaire).
  4. Clique sur le bouton transact, confirme dans MetaMask.
  5. La fonction retourne un tokenId (généralement 0 ou 1) : c'est le numéro unique de ton NFT.
Vérif : le NFT existe désormais ! Son image et ses métadonnées sont lisibles via l'URI IPFS.

I.2 Tester ownerOf (propriété)

  1. Toujours dans Remix, trouve la fonction ownerOf.
  2. Renseigne le tokenId obtenu à l'étape précédente.
  3. Clique sur le bouton call.
  4. Tu dois voir ton adresse MetaMask s'afficher : c'est le propriétaire du NFT — exactement ce que réclame le sujet.

I.3 Démonstration de sécurité

  1. Bascule sur ta deuxième adresse dans MetaMask (B.3).
  2. Appelle mintNFT depuis ce compte non-propriétaire.
  3. La transaction doit échouer avec le message Token42: only owner can mint.
À l'évaluation : montre ces appels dans Remix ou sur BSCScan — les transactions y sont visibles et vérifiables.

J Vérifier et publier sur BSCScan

Un block explorer est le "Google de la blockchain". On y rend notre contrat public et vérifiable.

Objectif : le contrat "Vérifié" sur BSCScan, avec la collection et les NFT affichés.

J.1 Trouver le contrat

  1. Va sur https://testnet.bscscan.com (le testnet, pas le mainnet !).
  2. Colle l'adresse du contrat dans la barre de recherche.
  3. La page du contrat s'affiche avec les transactions de mint. La collection y apparaît encore comme "Unknown" tant que ce n'est pas vérifié.

J.2 Vérifier le code source

  1. Ouvre l'onglet "Contract" puis clique "Verify and Publish".
  2. Remplis le formulaire exactement comme à la compilation :
    • Compiler type : Solidity (Single file)
    • Compiler version : celle choisie dans Remix (ex. 0.8.26)
    • Open Source License Type : MIT License
  3. Colle le code complet de Token42.sol dans le champ "Solidity Contract Code".
  4. Clique "Verify and Publish".
Si la vérification échoue : c'est presque toujours un paramètre différent de la compilation (version Solidity, licence, ou le code pas exactement identique). Recopie ton code depuis Remix tel quel.

J.3 Voir ton NFT

  2. Tu y verras le tokenId miné avec son propriétaire et ses métadonnées.
  3. Le lien IPFS de l'image doit être visible — ton NFT est désormais associé à son œuvre.
Résultat : ton NFT est vérifié, visible et son propriétaire est identifiable. C'est la preuve attendue.

L Dépannage & questions fréquentes

Les erreurs les plus courantes et leurs solutions.

L.1 "Not enough funds for gas"

Tu n'as pas assez de tBNB sur ton wallet testnet.

→ Récupère des tBNB au faucet (partie C) ou vérifie que MetaMask est bien sur le BSC Testnet (chain ID 97), pas sur Ethereum Mainnet.

L.2 La transaction reste "pending"

Le réseau de test est parfois lent ou le nonce de gas est bloqué.

→ Attends, ou dans MetaMask va dans Paramètres → Avancé → "Clear activity tab data" pour réinitialiser. Puis réessaie.

L.3 Mon image / mon JSON ne s'affiche pas

→ Vérifie le CID IPFS : le préfixe ipfs:// est-il bien présent dans le baseURI du contrat ? Le fichier est-il encore "épinglé" sur Pinata ? Teste le lien via la passerelle IPFS.

L.4 La vérification BSCScan échoue

→ Compare paramètre par paramètre avec Remix : version Solidity identique, licence MIT, et colle le code exact de Token42.sol (mêmes espaces, mêmes commentaires, c'est un hash qui doit matcher).

L.5 "revert" quand j'appelle mintNFT depuis un autre compte

Normal ! mintNFT est protégé par la vérification du propriétaire. C'est le comportement attendu et c'est exactement ce qu'il faut montrer à l'évaluation.

L.6 Est-ce que je risque de perdre de l'argent ?

Non. On ne travaille que sur la BSC Testnet avec des tBNB de test qui ne valent rien. N'utilise jamais le Mainnet ni des fonds réels.

Important : la partie bonus ne sera évaluée que si la partie obligatoire est PARFAITE (réalisée en intégralité et sans dysfonctionnement). Si une exigence obligatoire n'est pas satisfaite, le bonus ne sera pas évalué du tout. Commence donc toujours par valider les étapes A → L.

M.1 Créer un superbe NFT

Le visuel fait partie de l'évaluation qualitative du bonus. Quelques pistes pour soigner ton œuvre :

  • Pense collection : produis plusieurs variations cohérentes (même thème, mêmes couleurs) plutôt qu'un seul visuel ressemblant à un brouillon.
  • Réutilise le chiffre 42 comme fil conducteur artistique (reflet, ombre, motif, numéro d'édition…).
  • Soigne les métadonnées : descriptions travaillées, plusieurs attributs (cas M.2 et M.3 les consomment).
  • Choisis une résolution propre et un format classique (.png/.jpg).
Rappel : le chiffre 42 doit rester lisible et aucun contenu insultant n'est toléré.

M.2 Un site web pour miner son NFT

L'objectif est une interface graphique dans mint/ qui appelle ton smart contract via un bouton, sans passer par Remix.

  1. Récupère l'ABI du contrat (Remix → "Solidity Compiler" → bouton "ABI" → copie le JSON).
  2. Dans mint/, crée index.html qui charge ethers.js depuis un CDN et un bouton "Mint".
  3. Dans mint/app.js, connecte MetaMask, instancie le contrat avec son adresse + l'ABI, puis appel mintNFT(adresse).
  4. Affiche le tokenId retourné et le lien BSCScan de la transaction.

Extrait du cœur de app.js (à compléter et commenter) :

// Connexion MetaMask
const [account] = await provider.send("eth_requestAccounts", []);
const signer = provider.getSigner();

// Adresse de ton contrat déployé (H.3) + ABI copiée depuis Remix
const nft = new ethers.Contract(CONTRACT_ADDRESS, CONTRACT_ABI, signer);

async function mint() {
  const tx = await nft.mintNFT(account);   // seul le propriétaire peut mint
  await tx.wait();
  console.log("NFT miné ! tokenId :", tx.hash);
}
Sécurité : le bouton de mint fonctionne uniquement depuis le compte propriétaire (le require du contrat). D'autres visiteurs pourront voir la collection, mais pas miner.

M.3 Enregistrer métadonnées et image sur la blockchain

Le bonus demande de stocker les métadonnées (et idéalement l'image) directement sur la chaîne, pas seulement sur IPFS. Approche recommandée : JSON encodé en base64 comme tokenURI.

  1. Encode metadata.json en base64 (ex. via un site/outil base64 en ligne).
  2. Préfixe le résultat avec data:application/json;base64,.
  3. Dans le contrat, ajoute une fonction permettant de mettre à jour le URI d'un token passé : 
    function setTokenURI(uint256 tokenId, string memory uri) public {
    require(msg.sender == owner, "Token42: only owner");
    _setTokenURI(tokenId, uri);
}
  4. Appelle setTokenURI (depuis Remix ou ton site de mint M.2) avec le JSON base64 → les métadonnées sont désormais en chaîne.
  5. Dans BSCScan (partie J), l'onglet "Read Contract → tokenURI" doit renvoyer ton data:... et le NFT s'affiche sans dépendre d'IPFS pour le texte.
L'image reste sur IPFS : encodée en base64 on-chain, une image est trop lourde et coûterait un gas énorme. Le compromis standard : les métadonnées texte (JSON) sont sur la blockchain, le champ image du JSON référence le fichier sur IPFS. C'est ce qui se pratique dans la majorité des collections.
M.2 + M.3 combinés : ton site de mint peut proposer un second bouton "Appliquer métadonnées" qui appelle setTokenURI. Un seul fichier app.js pour tout gérer.
